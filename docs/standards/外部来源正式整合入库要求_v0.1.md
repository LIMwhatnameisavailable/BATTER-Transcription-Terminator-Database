# 外部来源正式整合入库要求 v0.1

本文件面向已经完成文献搜集、数据入口定位或初步坐标核验的协作者，说明如何把一批“候选外部来源”正式交接给 BTED。它与[新增文献收集与入库指南](协作者_新增文献收集与入库指南.md)配套使用。

## 1. 一条总原则

**找到数据不等于已经入库。**

外部来源先进入 `to_review`；只有完成参考版本、坐标、链方向、原始文件和端点级可追溯性核验后，才可进入 `standardized`。只有经发布检查后，才可进入 `published` 并显示在公开目录、下载区或 JBrowse。

协作者可以提交来源发现、数据入口和初步核验结论；维护者不应因“文献中有坐标表”或“其他论文已重分析过该数据”而跳过正式入库步骤。

## 2. 先判断来源属于哪一种情形

| 情形 | 可否进入正式流程 | 正确处理 |
|---|---|---|
| 作者在论文补充表中发表实验支持的 3′ end 坐标 | 可以 | 登记为 `author_called_endpoint`；完成坐标与链方向核验后建立端点表 |
| 已发表的算法对公开实验信号重分析并给出端点 | 可以，但须单独标识 | 在团队正式采纳 `algorithm_called_endpoint` 前，暂填 `NA` + `to_review`；不得称为原作者直接发表的端点，也不得称为预测 |
| 与本库已有来源使用同一原始数据、仅作重复重分析 | 不作为新端点来源 | 保留重复关系和依据，放入审计记录；不建立第二份公开端点表 |
| 纯预测或实验与预测无法拆分的混合表 | 不可以公开收录 | 标记 `prediction_only` / `author_integrated_mixed_evidence`，仅内部审计 |
| 参考版本、contig、坐标体系或链方向无法核实 | 暂不可以 | 标记 `blocked` 或 `to_review`，写明恢复条件；不得猜测或补齐 |

“算法重分析”与“预测”不同：前者的端点来自公开实验测序信号，但坐标由后续算法调用；后者没有对应的实验端点证据。两者的来源链和公开文案必须清晰区分。

## 3. 正式交接包：提交什么，放在哪里

一次外部来源交接以一个**批次**为单位，例如 `2026-08-09_fuchs-cascino-termite`。不得直接修改原始来源表的列结构。

| 产物 | 建议路径 | 要求 |
|---|---|---|
| 原始来源登记快照 | `data/registry/submissions/<batch_id>_source_intake.tsv` | 使用 26 列模板；保留交接时的原始填写内容；一行一个可独立处理来源 |
| 批次整合说明 | `docs/integration/<batch_id>.md` | 写清来源数量、重复关系、证据类别、纳入决定、未解决问题及下一位处理人 |
| 逐来源处理记录 | `docs/sources/<source_id>/README.md` | 正式接收后每个来源一份；记录下载 URL、文件名、SHA-256、坐标依据、统计、失败过程与剩余风险 |
| 小型端点标准表 | `data/records/<source_id>/<source_id>_endpoints.tsv` | 只在标准化通过后建立；必须符合 24 列端点 schema，不放原始 xlsx/FASTQ/BAM |
| 排除或冲突记录 | `data/audit/excluded_or_blocked_sources.tsv` | 重复来源、缺失坐标、不可发布证据均在此留痕，写明恢复条件或重复对象 |

如上述目录尚未存在，可在**专门的结构 PR**中先创建 README 说明目录用途；不要把原始 Excel、FASTQ、BAM、BigWig、PDF 或本地下载缓存提交到 GitHub。

## 4. 每条来源的入库门槛

来源从 `to_review` 进入 `standardized` 前，必须逐项完成：

1. **来源可追溯**：论文 PMID/DOI、原始数据 accession、补充表或端点文件 URL 已记录；原始文件在本地冻结，并记录文件名、下载日期和 SHA-256。
2. **实验范围明确**：物种、菌株、样本/条件、实验方法与端点来源文件已对应；一篇论文中的不同物种、菌株、参考版本或独立条件要拆为不同 `source_id`。
3. **参考与坐标明确**：论文实际参考 accession（含版本）、assembly、contig 清单、坐标体系和链定义均有原文或可复核证据。多复制子必须逐 contig 核验，不能跨 contig 匹配。
4. **端点可回溯**：每一个标准化端点能回到作者表行号，或回到已发表重分析的输出文件、算法版本、参数和上游 accession。
5. **统一格式正确**：生物学坐标为 1-based；单碱基 BED 始终为 `start = position - 1`、`end = position`；`end_id` 必须包含 source、sample、contig、strand 和序号。
6. **问题不隐藏**：无法判定的行要保留在审计记录，标记 `to_review` 或 `blocked`；不能为了凑齐端点表而推测链方向或参考版本。

进入 `published` 前还必须完成：派生文件 checksum、处理摘要、下载文件检查、端点表字段检查，以及（如有）JBrowse 配置检查。证据层和发布边界见[证据分层与发布边界](证据分层与发布边界.md)。

## 5. 分支与 PR：不要直接合并“资料搜集分支”

来源搜集分支通常同时包含调研笔记、临时验证和项目入口文件改动。**不要把这类分支整体 merge 到当前项目分支。** 推荐流程：

1. 协作者保留自己的来源搜集分支，整理出上述“正式交接包”。
2. 从当前公共基线新建整合分支，例如 `feature/integrate-2026-08-external-sources`。
3. 只选择性接收来源登记快照、可复现核验材料和整合说明；根目录 README、全局模板或网站文件只有在本次任务确有必要且单独评审后才改动。
4. 先开 Draft PR，目标分支为当前项目公共基线；PR 中逐项写出“接收了什么、没有接收什么、为什么”。
5. 对每个 `source_id` 单独开后续标准化 PR；不要把十几条来源的端点转换打包为一次不可审查的大型提交。

若来源搜集分支落后于目标分支，应先 rebase 或在新的整合分支中选择性迁移文件，避免覆盖已经确定的项目结构和 README。

## 6. 外部来源整合说明模板

批次说明可按以下最小格式撰写：

```md
# <batch_id> 外部来源整合说明

## 范围
- 交接来源数：
- 论文数：
- 拟进入正式审计的 source_id：
- 重复/排除的 source_id：

## 接收决定
| source_id | 证据类别 | 当前状态 | 决定 | 主要依据 | 未解决问题 |
|---|---|---|---|---|---|

## 未接收内容
- 原因：例如原始文件未冻结、坐标定义缺失、与既有来源重复、仅为预测等。

## 下一步与负责人
- <source_id>：补充参考版本与坐标核验；负责人：
- <source_id>：建立标准端点表；负责人：

## 本地验证
- `python3 scripts/validate_bted_templates.py`
- `git diff --check`
```

## 7. 合并前检查清单

- [ ] 未改动 26 列来源表与 24 列端点表的表头；如确需新增枚举值，已先提交字典提案并获得团队确认。
- [ ] 每条拟接收来源均有唯一 `source_id`，不存在与现有注册表冲突的编号。
- [ ] 重复来源已写明其重复对象，且不会产生第二份公开端点表。
- [ ] 算法重分析端点与作者直接发表端点、预测结果没有混写。
- [ ] 所有坐标结论都附有可复查的原始表、URL、轻量验证脚本或文本结果；文档不能只引用未提交的本地文件。
- [ ] 没有提交原始测序文件、出版商附件、本地绝对路径、缓存或凭据。
- [ ] 运行 `python3 scripts/validate_bted_templates.py` 与 `git diff --check`；如修改站点，再运行 `python3 scripts/validate-site.py`。
