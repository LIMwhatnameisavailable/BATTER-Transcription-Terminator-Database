**建议时长：** 5–7 分钟

**合并 `main` 后的公开演示网址：** <https://seu-yolo.github.io/BATTER-Transcription-Terminator-Database/>

**开发分支：** <https://github.com/seu-yolo/BATTER-Transcription-Terminator-Database/tree/agent/assembly-track-download-demo>
**演示重点：** 数据库的组织逻辑与使用方式，不展开常规文件格式细节。

1. 使用 Chrome 或 Edge，建议开无痕窗口，浏览器缩放设为 100%。
2. 如果新版分支尚未合并到 `main`，优先使用下方本地预览；当前公开网址仍可能显示旧版。
3. 提前打开以下三个页面，减少现场等待：
   - 网站首页；
   - `GCF_000739105.1` 组装详情页；
   - 下载页。
4. 保留本地预览作为网络故障备份：

   ```bash
   cd /Users/seu_yolo/Desktop/BGIRNA/.worktrees/assembly-track-download-demo
   python3 -m http.server 8012 --directory .pages-preview
   ```

   然后访问 `http://localhost:8012/`。
5. 现场只演示一个 JBrowse 例子。JBrowse 资产较大，首次加载可能需要数秒。

## 二、推荐展示顺序和讲法

### 1. 首页：先讲数据库如何组织（约 40 秒）

打开首页，指向四个数字：

- 20 个参考组装；
- 22 个来源 track；
- 28,399 条端点记录；
- 21 个可浏览 track。

可以直接说：

> 我们把 BATTER Table S1 中的 22 个来源整理成了当前演示版本。新版网站不再把每篇来源直接当成一个“基因组”，而是按精确的参考组装组织，所以 22 个来源对应 20 个组装。相同组装上的不同研究保留为独立 track，方便比较，也不会把它们误合并成一个结论。

### 2. Genomes：展示“同一基因组、多条 track”（约 1 分钟）

点击顶部 **Genomes**。

先说明一行代表一个完整 assembly accession，而不是一篇文章。随后找到：

- `GCF_000739105.1`：2 个 track，2,848 条记录；
- `GCF_005519465.1`：2 个 track，2,567 条记录。

点击 `GCF_000739105.1`。

可以说：

> 这个参考组装在两项研究中都使用过。现在它只占一个基因组入口，下面列出两个来源、年份、文献、证据类别和各自记录数。合并的是网页入口和浏览器视图，不是把两批记录去重，也不是生成共识终止子。

### 3. 组装详情与 JBrowse：展示可追溯性（约 1.5 分钟）

在组装详情页依次指出：

1. assembly accession 与物种；
2. source tracks 数量；
3. 两条来源记录及其 PMID；
4. BED 和 metadata 两个下载入口。

点击 **Open genome browser**。新版配置会自动打开一个局部区域，并显示：

- NCBI gene annotation；
- `BATTER_S1_007` 来源 track；
- `BATTER_S1_013` 来源 track。

可以说：

> JBrowse 中每条 track 的名字都带有 source ID，研究者可以在同一参考坐标下比较不同论文的端点分布，再回到来源页面查看文章、原始数据 accession 和证据说明。

不要说“两个 track 重合就证明该位点是真实终止子”。更准确的说法是：

> 多来源一致可以作为后续筛选线索，但是否构成功能性终止证据仍取决于原实验和证据类型。

### 4. Download：展示选择下载（约 1 分钟）

点击顶部 **Download**：

1. 点击 **Clear**；
2. 勾选 `GCF_000739105.1` 和 `GCF_005519465.1`；
3. 确认顶部显示 **2 genomes selected · 5,415 records**；
4. 点击 **Download selected (.zip)**。

下载后 ZIP 中应有两个独立目录，每个目录包含：

- `endpoints.bed`：该组装下的标准坐标记录；
- `metadata.json`：来源、论文、accession、证据类别、限制和 BED 校验值。

可以说：

> 下载页改成以基因组为单位选择，支持全选或多选。用户界面只保留最常用的 BED 和一份合并 metadata；更详细的内部表、字段字典和处理记录仍在仓库中保留，但不再占据主要下载界面。

### 5. 收尾：讲下一步（约 40 秒）

可以说：

> 这一版主要先确定数据库入口、同组装多 track、证据边界和下载接口。下一步会继续核查组装归并规则、完善 track 显示名称和元数据字段，并在老师确认界面逻辑后，把同一套流程用于新增来源。

## 三、老师意见与本版对应关系

| 老师意见 | 本版处理 |
|---|---|
| 同一个基因组可以合并，用不同 track 展示 | 22 个来源按完整 assembly accession 聚合为 20 个组装；两组重复参考各生成多 track JBrowse |
| 下载需要全选或选择几个基因组 | 新增全选、清空、多选和浏览器端 ZIP 打包 |
| 常规格式内容不必突出 | 来源页移除坐标换算、再分发等常规字段的主展示 |
| 文件太多，只保留重要 BED，其余整理为 metadata | 主要下载界面只展示 `endpoints.bed` 与 `metadata.json` |
| Source 与 Downloads 内容重复 | Genomes 用于浏览与比较，Download 专门用于批量获取，两页职责分开 |

## 四、可能被问到的问题

### 为什么 22 个来源只有 20 个基因组？

因为两对来源使用完全相同的参考组装 accession。数据库按组装建立入口，但各来源仍保留为独立 track，所以没有丢数据。

### 为什么不能按物种名称直接合并？

同一物种可能使用不同菌株或不同参考版本。只有完整 assembly accession 相同，并且参考序列核查一致时才共用坐标视图。

### S1_002 为什么只有 metadata？

该来源当前不能从混合表中稳定拆出纯实验端点。为了避免发布含义不清的坐标，暂时只保留来源审计信息，不提供 BED 或 JBrowse。

### BED 是什么？

BED 是基因组区间的通用文本格式，可供 JBrowse、UCSC 类浏览器和常见基因组工具读取。本网站的单碱基端点使用 BED6，并保留 contig、位置、稳定 `end_id` 和链方向。

### 相同组装的记录是否被去重？

没有。组装级 BED 是各来源 BED 的顺序汇集，每条记录继续保留来源特异的 `end_id`。网页聚合不改变证据，也不生成共识集合。

### 能不能继续加入新数据？

可以。新增来源先完成来源登记、参考组装与坐标核验、证据分类和 BED/metadata 生成；若 assembly 已存在，则成为新 track，否则建立新的基因组入口。

## 五、现场故障处理

- **网页打不开：** 使用本地 `http://localhost:8012/`。
- **JBrowse 加载慢：** 跳过实时缩放，直接说明组装详情页已列出两个来源 track；不要反复刷新。
- **JBrowse 出现旧会话：** 用无痕窗口重新打开组装页，再点 **Open genome browser**。
- **下载未开始：** 确认至少勾选一个组装；现场可只演示勾选和预计文件结构。
- **时间不足：** 只演示首页 → `GCF_000739105.1` → JBrowse → Download 四步。

## 六、展示边界

- 这是数据库和网站工程演示，不是新的生物学发现。
- 不把 `3′ end`、候选峰或预测注释统一称为“已验证终止子”。
- 不因多个来源坐标接近就宣称存在功能性共识。
- 不隐藏来源、参考版本或 `audit_only` 状态。
- 不在网页层面修改已经冻结的 28,399 条公开记录。
